# Use Cases

Канонические сценарии MVP v1 после доменной коррекции. Они уточняют [[mvp-scope]], следуют [[decision-provenance]] и не вводят серийную идентификацию деталей.

## Общие условия

- подготовленные паспорта, operation scopes и нормы являются read-only seed-данными технолога/БТБ;
- `PLANNER` представляет интерактивные обязанности ПДБ;
- `MASTER` назначает карточки и фиксирует начало/завершение; `WORKER` не отправляет lifecycle-команды;
- `AcceptFirstArticle`, отдельная `RecordFinalBatchAcceptance` и синтетическое per-card закрытие WorkCard имеют разный смысл;
- изменяющая команда содержит версии всех существующих изменяемых агрегатов;
- успех сохраняет полный предметный результат и audit events атомарно, отказ не имеет побочных эффектов;
- HTTP-маршруты и коды появятся в [[api-contracts]].

## UC-001. Создать производственную партию

**Цель:** создать партию с количеством и снимком выбранного подготовленного паспорта.

**Актор:** `PLANNER` как представитель ПДБ.

**Предусловия:** паспорт существует и содержит валидные operation plans; quantity — положительное целое.

**Основной поток:**

1. Планировщик выбирает паспорт из read-only списка и вводит quantity.
2. Backend проверяет роль, паспорт и количество.
3. Система создаёт невыпущенную `ProductionBatch` версии `1` со снимком паспорта.
4. Система сохраняет `ProductionBatchCreated`.

**Результат:** партия не содержит одного `normHours`; комплектов и карточек пока нет.

**Отказы:** `NS-001`, `NS-002`, `NS-025`.

**Правила:** `BR-001`, `BR-003`, `BR-004`, `BR-010`, `BR-011`, `BR-050`, `BR-051`.

## UC-002. Выпустить комплекты карточек

**Цель:** один раз атомарно создать все комплекты и карточки снимка паспорта.

**Актор:** `PLANNER`.

**Предусловия:** партия существует, не выпускалась, версия актуальна.

**Основной поток:**

1. Экран показывает план нескольких operation scopes и общее число карточек.
2. Планировщик подтверждает выпуск.
3. Система создаёт `WorkCardSet` для каждого operation plan со своей нормой, `plannedCardCount` и gate `FIRST_ARTICLE_PENDING`.
4. Система создаёт карточки с уникальными UUID и `batchQuantitySnapshot`, без sequence/номера детали.
5. Партия и все события фиксируются одной транзакцией.
6. Для fixture `112` результат равен `112 + 112 + 26 = 250`.

**Результат:** у партии несколько комплектов; сумма карточек может превышать quantity.

**Отказы:** `NS-003`–`NS-005`, `NS-026`–`NS-028`.

**Правила:** `BR-002`–`BR-004`, `BR-012`–`BR-016`, `BR-050`–`BR-062`.

## UC-003. Назначить карточки

**Цель:** атомарно назначить карточки одного комплекта одному исполнителю с purpose, не нумеруя детали.

**Актор:** `MASTER`.

**First-article поток:**

1. Для `FIRST_ARTICLE_PENDING` мастер выбирает ровно одну `RELEASED` карточку по внутреннему UUID и одного `WORKER`.
2. Система атомарно регистрирует `firstArticleWorkCardId`, purpose `FIRST_ARTICLE`, assignee и `ASSIGNED`.

**Serial поток:**

1. После `SERIAL_ALLOWED` мастер выбирает непустой набор `RELEASED` одного комплекта и одного `WORKER`.
2. Система проверяет комплект, все карточки и версии.
3. Все карточки получают purpose `SERIAL`, assignee и `ASSIGNED` либо не меняется ни одна.
4. Последовательные команды формируют распределение; в fixture first-article карточка входит в долю `60`, затем назначаются ещё `59` тому же исполнителю и `52` другому: итог `60 + 52 = 112`.

**Отказы:** `NS-006`–`NS-009`, `NS-029`.

**Правила:** `BR-020`–`BR-024`, `BR-050`–`BR-062`.

## UC-004. Зафиксировать выполнение карточки

**Цель:** мастеру зафиксировать начало и завершение назначенной работы.

**Актор:** `MASTER`; `assigneeId` указывает фактического исполнителя и не обязан совпадать с `actorId`.

**Основной поток:**

1. Мастер открывает `ASSIGNED` карточку.
2. Система проверяет роль, purpose, gate, состояние и версию; `StartWorkCard` переводит её в `IN_PROGRESS`.
3. После работы мастер выполняет `CompleteWorkCard` с новой версией.
4. Карточка становится `COMPLETED` и ожидает положительного действия БТК.

**Отказы:** команда `WORKER`, неверный gate/state или конфликт отклоняются по `NS-004`, `NS-010`–`NS-013`.

**Правила:** `BR-030`, `BR-031`, `BR-050`–`BR-061`.

## UC-005. Положительно принять первую деталь

**Цель:** открыть серийную работу operation-scoped комплекта.

**Актор:** `QUALITY_CONTROLLER`.

**Предусловия:** зарегистрированная first-article карточка `COMPLETED`; комплект `FIRST_ARTICLE_PENDING`; обе версии актуальны.

**Основной поток:** БТК выполняет `AcceptFirstArticle`; система атомарно закрывает карточку, переводит gate в `SERIAL_ALLOWED` и сохраняет `WorkCardQualityConfirmed`/`FirstArticleAccepted`.

**Результат:** серийное назначение/выполнение комплекта разрешено; UUID карточки не становится номером первой физической детали.

**Отказы:** `NS-014`, `NS-015`, `NS-018`.

**Правила:** `BR-032`, `BR-034`, `BR-035`, `BR-050`–`BR-062`.

## UC-006. Выполнить цифровое per-card подтверждение и закрыть WorkCard

**Цель:** синтетическим TO-BE-действием положительно завершить lifecycle одной серийной WorkCard, не записывая финальную приёмку всей партии.

**Актор:** `QUALITY_CONTROLLER`.

**Предусловия:** purpose `SERIAL`, состояние `COMPLETED`, комплект `SERIAL_ALLOWED`, версия актуальна.

**Основной поток:** БТК выполняет `ConfirmWorkCardQuality`; система переводит только выбранную карточку в `CLOSED` и сохраняет `WorkCardQualityConfirmed` с `confirmationScope: WORK_CARD`, `acceptanceType: SERIAL`.

**Граница:** `CLOSED` не означает `FinalBatchAcceptance`. Отдельная digital-команда уровня партии описана в `UC-015`, а подписи БТК на физических карточках не оцифровываются.

**Отказы:** `NS-016`–`NS-018`.

**Правила:** `BR-033`–`BR-035`, `BR-050`–`BR-061`.

## UC-007. Просмотреть производственные данные

**Цель:** видеть подготовленный паспорт, партию, operation-scoped комплекты, распределение и карточки без изменения данных.

**Актор:** доверенная demo-роль согласно матрице чтения.

**Основной поток:** система возвращает структуру происхождения, нормы комплектов, gate, counts и технические UUID. UI не показывает UUID как номер детали и не создаёт `#01`/`3 из 112`. Provenance-представление явно различает `FirstPieceAcceptance`, подтверждённую `FinalBatchAcceptance` всей партии и синтетическое per-card `WorkCardQualityConfirmation`.

**Результат:** версии и события не изменены.

## UC-008. Восстановить историю

**Актор:** `ADMIN_AUDITOR`.

**Основной поток:** система возвращает события карточки и связанных контекстов с версией, субъектом, `commandId` и `correlationId`, упорядоченные детерминированно.

**Отказы:** `NS-019`, `NS-034`, `NS-036`.

**Правила:** `BR-050`–`BR-053`.

## UC-009. Экспортировать закрытую карточку

**Актор:** `ADMIN_AUDITOR`.

**Предусловия:** карточка `CLOSED`, имеет assignee и актуальную версию.

**Основной поток:** первый export создаёт одну `PayrollRecord` с operation-scoped norm snapshot и событие; повтор возвращает ту же запись без нового факта.

**Отказы:** `NS-020`, `NS-021`, `NS-037`–`NS-040`.

**Правила:** `BR-040`–`BR-044`.

## UC-010. Переключить demo-роль

Система меняет только доверенный session context, перечитывает permissions и очищает permission-sensitive UI. Партии, комплекты, карточки, версии и audit не меняются. Неизвестная роль не активируется (`NS-024`, `NS-025`, `NS-031`).

## UC-011. Проверить структуру и распределение

**Актор:** `PLANNER` или `MASTER`.

1. Актор открывает партию `112` и видит три комплекта `112`, `112`, `26` и total `250`.
2. В каждом комплекте видны operation scope, собственная норма, gate и planned/actual count.
3. Карточки показывают UUID только как технический ID и `batchQuantitySnapshot = 112`; sequence отсутствует.
4. Первый полный комплект показывает assignment summary `60 + 52 = 112`.

**Результат:** проверена модель количеств без индивидуальной прослеживаемости деталей и без ложного вывода финальной приёмки партии из статусов WorkCard.

**Правила:** `BR-012`–`BR-015`, `AC-BAT-002`, `AC-ASG-001`, `AC-READ-002`.

## UC-012. Восстановиться после конфликта

После version conflict клиент не меняет данные и не повторяет команду автоматически. Пользователь перечитывает карточку/комплект/партию, оценивает новое состояние и при допустимости формирует новую осознанную команду с актуальными версиями.

**Правила:** `BR-002`, `BR-060`–`BR-062`.

## UC-013. Просмотреть payroll-запись

`ADMIN_AUDITOR` читает ID, `workCardId`, бенефициара, operation-scoped norm snapshot и время без повторного export или изменений.

## UC-014. Сопоставить массовую операцию

Аудитор открывает audit-контекст по `correlationId` и сопоставляет полный набор событий выпуска, назначения или first-article acceptance с предметным результатом. UX не фиксирует endpoint; архитектура должна обеспечить доказуемо полный набор.

## UC-015. Зафиксировать финальную приёмку завершённой партии

**Цель:** отдельным positive-only действием подтвердить всю завершённую `ProductionBatch`, не выводя приёмку автоматически из карточек и не имитируя физическую подпись.

**Актор:** `QUALITY_CONTROLLER`.

**Предусловия:** партия выпущена; каждый обязательный `WorkCardSet` имеет `SERIAL_ALLOWED`, полный `plannedCardCount` и только `CLOSED` WorkCard; `FinalBatchAcceptance` отсутствует; `expectedVersion` партии актуальна.

**Основной поток:**

1. БТК открывает `S-03` и видит раздельные признаки: first-article gates пройдены, все необходимые serial-карточки закрыты, финальная приёмка ещё не записана.
2. БТК подтверждает `RecordFinalBatchAcceptance` с `batchId`, `expectedVersion` и `commandId`.
3. Backend проверяет доверенную роль, версию и completion predicate по транзакционно согласованному состоянию.
4. Одна транзакция создаёт неизменяемую `FinalBatchAcceptance`, связывает её с партией, переводит партию в `FINAL_ACCEPTED`, увеличивает версию и сохраняет `FinalBatchAccepted`.
5. Read-back показывает `acceptanceId`, актора, время и результирующую версию партии.

**Повтор:** replay того же `commandId` возвращает существующую запись без второй версии/события; новый command после успеха отклоняется как терминальный конфликт.

**Отказы:** `NS-002`, `NS-004`, `NS-023`, `NS-041`–`NS-045`.

**Правила:** `BR-001`–`BR-003`, `BR-036`–`BR-039`, `BR-050`–`BR-062`.

## Сквозной порядок

Core demo sequence: `UC-001 → UC-002 → UC-003(first article) → UC-004 → UC-005 → UC-003(serial) → UC-004 → UC-006 → UC-015 → UC-009`. После демонстрации одной serial WorkCard прототип использует подготовленное all-closed состояние остальных карточек, чтобы показать aggregate-level приёмку без ручного прогона `250` записей. `UC-006` остаётся только синтетическим per-card закрытием; `UC-015` отдельно создаёт `FinalBatchAcceptance`. `UC-007`, `UC-008`, `UC-010`–`UC-014` обеспечивают read/provenance и supporting-сценарии.
