# Business Rules

Канонические бизнес-инварианты MVP v1. Идентификаторы `BR-*` устойчивы; скорректированная семантика зафиксирована решениями `D-013`–`D-021` в [[decision-log]].

## Общие правила команд

| ID | Правило |
|---|---|
| BR-001 | Любая изменяющая бизнес-команда выполняется только после проверки доверенной роли на backend; состояние UI не авторизует действие. |
| BR-002 | Команда над существующим изменяемым агрегатом передаёт `expectedVersion`; межагрегатная команда передаёт версии всех изменяемых целей. Несовпадение отклоняет всю команду. |
| BR-003 | Неуспешная команда не изменяет предметное состояние и не создаёт доменное/audit event об успехе. |
| BR-004 | ID паспорта-снимка, партии, комплекта, карточки, финальной приёмки и payroll-записи неизменяемы; `WorkCardId` является внутренним UUID, а не номером детали. |

## Партия и выпуск

| ID | Правило |
|---|---|
| BR-010 | Количество партии — положительное целое число; выбранный подготовленный паспорт существует и содержит непустой валидный operation plan. |
| BR-011 | `ProductionBatch` хранит `batchQuantity` и снимок паспорта, но не хранит один `normHours`; нормы принадлежат operation scopes. |
| BR-012 | Выпуск допустим один раз и создаёт один или несколько `WorkCardSet` согласно снимку паспорта. Одна партия может иметь много комплектов. |
| BR-013 | Каждый комплект получает одну операцию/группу, положительную норму и положительный `plannedCardCount`; атомарный выпуск создаёт все комплекты и сумму их карточек либо ничего. Сумма не обязана равняться `batchQuantity`. |
| BR-014 | Каждая `WorkCard` уникальна по внутреннему UUID, не имеет `sequenceNumber` и содержит неизменяемый `batchQuantitySnapshot`; равенство количества карточек комплекта количеству партии не идентифицирует детали. |
| BR-015 | Комплект и карточка получают неизменяемые снимки operation scope и нормы из паспорта; `WorkCard` получает норму своего комплекта, а не партии. |
| BR-016 | Повторный выпуск, перевыпуск и интерактивное изменение паспорта/норм не поддерживаются в MVP. |

## Назначение

| ID | Правило |
|---|---|
| BR-020 | `AssignWorkCards` содержит непустой набор различных карточек одного комплекта, одного существующего `WORKER` и `purpose = FIRST_ARTICLE | SERIAL`. |
| BR-021 | При `FIRST_ARTICLE_PENDING` допустимо назначить ровно одну ещё неназначенную `RELEASED` карточку с purpose `FIRST_ARTICLE`, если комплект ещё не хранит `firstArticleWorkCardId`. Назначение `SERIAL` разрешено только при `SERIAL_ALLOWED`. |
| BR-022 | Перед изменением проверяются комплект и все карточки. Ошибка состояния, версии, исполнителя или gate отклоняет весь набор без частичного назначения. |
| BR-023 | Успешное назначение записывает одного `assigneeId`, фиксирует неизменяемый purpose при первом назначении и переводит каждую карточку `RELEASED → ASSIGNED`; first-article assignment также атомарно регистрирует карточку в комплекте. |
| BR-024 | Переназначение, снятие назначения и изменение purpose не входят в MVP. |
| BR-025 | В каноническом fixture first-article карточка входит в долю первого исполнителя: `1 + 59 + 52 = 60 + 52 = 112`. Итог выражается количествами назначений, а не диапазонами или номерами деталей. |

## Выполнение и контроль

| ID | Правило |
|---|---|
| BR-030 | `StartWorkCard` может выполнить только `MASTER` для назначенной карточки `ASSIGNED`. First-article карточка допускается при `FIRST_ARTICLE_PENDING`; serial-карточка — только при `SERIAL_ALLOWED`. Результат — `IN_PROGRESS`. |
| BR-031 | `CompleteWorkCard` может выполнить только `MASTER` для карточки `IN_PROGRESS`; результат — `COMPLETED`. Назначенный `WORKER` не отправляет обе команды. |
| BR-032 | `AcceptFirstArticle` выполняет `QUALITY_CONTROLLER` для зарегистрированной first-article карточки `COMPLETED` и комплекта `FIRST_ARTICLE_PENDING`. Успех атомарно переводит карточку в `CLOSED`, комплект в `SERIAL_ALLOWED` и фиксирует положительную приёмку. |
| BR-033 | `ConfirmWorkCardQuality` выполняет `QUALITY_CONTROLLER` для одной serial-карточки `COMPLETED` только при `SERIAL_ALLOWED`; синтетический per-card успех атомарно переводит только эту карточку в `CLOSED`. |
| BR-034 | Отрицательная first-article/final-batch acceptance, причины брака, отклонение БТК, возврат и доработка не входят в MVP. |
| BR-035 | `CLOSED` — терминальное состояние; отдельной команды закрытия и повторного подтверждения нет. |
| BR-036 | `FirstPieceAcceptance`, `FinalBatchAcceptance` и цифровое закрытие WorkCard не взаимозаменяемы. `ConfirmWorkCardQuality` и даже все `CLOSED` карточки не являются записью финальной приёмки партии; её создаёт только отдельная `RecordFinalBatchAcceptance`, не заменяющая физические подписи БТК. |
| BR-037 | `RecordFinalBatchAcceptance` выполняет только `QUALITY_CONTROLLER` для выпущенной партии: у каждого обязательного `WorkCardSet` first-article gate равен `SERIAL_ALLOWED`, фактическое число карточек равно `plannedCardCount`, все необходимые WorkCard имеют `CLOSED`, а `FinalBatchAcceptance` отсутствует. Проверка выполняется по транзакционно согласованному состоянию. |
| BR-038 | Успех `RecordFinalBatchAcceptance` при актуальном `expectedVersion` атомарно создаёт одну неизменяемую `FinalBatchAcceptance`, связывает её с `ProductionBatch`, переводит партию в `FINAL_ACCEPTED`, увеличивает версию партии на один и сохраняет `FinalBatchAccepted`. Уникальность `batchId` запрещает вторую запись. |
| BR-039 | Повтор с тем же `commandId` идемпотентно возвращает созданную `FinalBatchAcceptance` без новой записи, версии или события. Новая команда для уже принятой партии отклоняется как терминальный конфликт. |

## Mock payroll export

| ID | Правило |
|---|---|
| BR-040 | Экспортировать можно только `CLOSED` карточку с назначенным исполнителем. |
| BR-041 | Для карточки существует не более одной `PayrollRecord`; `workCardId` — идемпотентный бизнес-ключ. |
| BR-042 | Первый export создаёт запись для назначенного исполнителя с неизменяемым `normHoursSnapshot` карточки. |
| BR-043 | Повтор возвращает существующую запись и не создаёт вторую запись или событие успеха. |
| BR-044 | Mock export не рассчитывает деньги, налоги, коэффициенты, фактическое время или выплаты. |

## Audit log и атомарность

| ID | Правило |
|---|---|
| BR-050 | **Каждая успешная изменяющая бизнес-команда** — `CreateProductionBatch`, `ReleaseWorkCards`, `AssignWorkCards`, `StartWorkCard`, `CompleteWorkCard`, `AcceptFirstArticle`, `ConfirmWorkCardQuality`, `RecordFinalBatchAcceptance` и первый `ExportWorkCardToPayroll` — создаёт audit event для каждого изменённого агрегата с уникальным ID, типом, временем, субъектом, объектом, командой, корреляцией и результирующей версией. |
| BR-051 | Изменение состояния и все соответствующие audit events фиксируются в одной транзакции. Частичное состояние или неполный набор событий недопустимы. |
| BR-052 | Audit events добавляются последовательно и не редактируются/не удаляются бизнес-командами. |
| BR-053 | История одного агрегата упорядочивается по версии и времени; для коррелированной межагрегатной операции сохраняются общий `correlationId` и исходный `commandId`. |

## Конкурентные изменения

| ID | Правило |
|---|---|
| BR-060 | Каждое успешное изменение изменяемого агрегата увеличивает его версию ровно на единицу. |
| BR-061 | При конфликте клиент получает явный отказ и перечитывает актуальное состояние; молчаливое перезаписывание запрещено. |
| BR-062 | Выпуск, first-article assignment, массовое назначение и first-article acceptance проверяют версии всех изменяемых агрегатов в общей транзакции. `RecordFinalBatchAcceptance` проверяет актуальную версию партии и завершённость всех связанных set/card по согласованному снимку в той же транзакции. |

## Канонические проверки кардинальности

- партия `112` выпускает три комплекта `112`, `112`, `26` и всего `250` карточек;
- каждая карточка хранит `batchQuantitySnapshot = 112`, но не номер экземпляра;
- первый полный комплект после последовательных атомарных назначений имеет распределение `60 + 52 = 112`;
- нормы комплектов могут различаться, и `ProductionBatch.normHours` отсутствует.
- `AcceptFirstArticle` моделирует первую приёмку, `ConfirmWorkCardQuality` — синтетическое per-card закрытие, а отдельная `RecordFinalBatchAcceptance` создаёт aggregate-level факт только после завершения всей партии.

## Приоритет правил

[[mvp-scope]] определяет границу, [[decision-provenance]] — происхождение, этот файл — инварианты, [[work-card-state-machine]] — переходы, [[roles-permissions]] — субъектов. Структурная согласованность без соответствия подтверждённому AS-IS недостаточна.

## Вне правил MVP v1

- физическая деталь, её серийный номер и индивидуальная трассировка;
- отрицательный контроль и доработка;
- фиксация физической подписи БТК, отрицательная финальная приёмка, причины брака и rework;
- переназначение, повторный выпуск, редактирование норм;
- реальные payroll-расчёты и интеграции.
