# Business Rules

Канонические бизнес-инварианты MVP v1. Идентификаторы `BR-*` устойчивы и будут использоваться в [[commands-events]], acceptance criteria и тестах.

## Общие правила команд

| ID | Правило |
|---|---|
| BR-001 | Любая изменяющая бизнес-команда выполняется только после проверки роли на backend; состояние UI не является механизмом авторизации. |
| BR-002 | Команда над существующим изменяемым агрегатом передаёт `expectedVersion`; несовпадение версии отклоняет команду как конфликт. |
| BR-003 | Неуспешная команда не изменяет предметное состояние и не создаёт доменное или audit event об успешном действии. Техническое логирование отказа допускается отдельно. |
| BR-004 | Идентификаторы партии, комплекта, карточки и записи начисления неизменяемы после создания. |

## Партия и выпуск карточек

| ID | Правило |
|---|---|
| BR-010 | Количество экземпляров партии — положительное целое число. |
| BR-011 | Нормо-часы партии — положительное десятичное значение; они не являются фактически отработанным временем или денежной суммой. |
| BR-012 | Выпуск допустим только для ранее не выпущенной партии. Для одной партии существует не более одного `WorkCardSet`. |
| BR-013 | Один успешный выпуск атомарно создаёт один `WorkCardSet` и ровно `N` карточек, где `N` равно количеству экземпляров партии. Частичный выпуск запрещён. |
| BR-014 | Каждая карточка выпуска уникальна по идентификатору и по паре `(workCardSetId, sequenceNumber)`; номера образуют диапазон от `1` до `N` без пропусков. |
| BR-015 | Карточка получает неизменяемые снимки маршрута и нормо-часов партии на момент выпуска. После выпуска исходные параметры партии в MVP не редактируются. |
| BR-016 | Повторный выпуск, перевыпуск и версионность нормы не поддерживаются в MVP v1. |

## Назначение

| ID | Правило |
|---|---|
| BR-020 | Массовое назначение содержит непустой набор различных карточек и одного исполнителя. |
| BR-021 | Назначить можно только карточку в состоянии `RELEASED`, у которой ещё нет исполнителя. |
| BR-022 | Перед изменением проверяются все выбранные карточки. Если хотя бы одна недоступна, имеет неверное состояние, версию или назначение, команда не меняет ни одну карточку. |
| BR-023 | Успешное назначение записывает одного исполнителя и переводит каждую карточку `RELEASED → ASSIGNED`. |
| BR-024 | Переназначение и снятие назначения не входят в MVP v1. |

## Выполнение и контроль

| ID | Правило |
|---|---|
| BR-030 | Начать работу может только назначенный исполнитель карточки в состоянии `ASSIGNED`; результат — `IN_PROGRESS`. |
| BR-031 | Завершить работу может только тот же назначенный исполнитель карточки в состоянии `IN_PROGRESS`; результат — `COMPLETED`. |
| BR-032 | Подтвердить выполнение может пользователь с ролью мастера только для карточки `COMPLETED`; результат — `MASTER_CONFIRMED`. |
| BR-033 | Подтвердить качество может пользователь с ролью контролёра БТК только для карточки `MASTER_CONFIRMED`. Успех атомарно фиксирует подтверждение БТК и переводит карточку в `CLOSED`. |
| BR-034 | В MVP v1 контролёр БТК не может отклонить карточку. Отклонение и доработка относятся к итерации 2. |
| BR-035 | `CLOSED` — терминальное состояние: назначение, выполнение и повторные подтверждения запрещены. |

## Mock payroll export

| ID | Правило |
|---|---|
| BR-040 | Экспортировать можно только закрытую карточку с назначенным исполнителем. |
| BR-041 | Для одной карточки существует не более одной `PayrollRecord`; `workCardId` служит идемпотентным бизнес-ключом. |
| BR-042 | Первый успешный экспорт создаёт запись для назначенного исполнителя с неизменяемым снимком нормо-часов карточки. |
| BR-043 | Повтор той же команды возвращает существующий результат и не создаёт вторую запись начисления или второе событие успешного экспорта. |
| BR-044 | Mock export не рассчитывает зарплату, налоги, коэффициенты, фактическое время или реальные выплаты. |

## Audit log и атомарность

| ID | Правило |
|---|---|
| BR-050 | Каждая успешная команда выпуска, назначения, перехода состояния и первого экспорта создаёт audit event с уникальным ID, типом, временем, субъектом, объектом и версией агрегата. |
| BR-051 | Изменение предметного состояния и соответствующий audit event фиксируются в одной транзакции. Состояние без события и событие без состояния недопустимы. |
| BR-052 | Audit events добавляются последовательно и не редактируются и не удаляются бизнес-командами. |
| BR-053 | История карточки упорядочивается по версии агрегата и времени события; при равном времени версия определяет порядок. |

## Конкурентные изменения

| ID | Правило |
|---|---|
| BR-060 | Каждое успешное изменение агрегата увеличивает его версию ровно на единицу. |
| BR-061 | При конфликте версии клиент получает явный конфликт и должен перечитать актуальное состояние; автоматическое молчаливое перезаписывание запрещено. |
| BR-062 | Выпуск и массовое назначение проверяют версии всех затрагиваемых агрегатов внутри общей транзакции. |

## Приоритет правил

Если документы расходятся, [[mvp-scope]] определяет продуктовую границу, этот файл — инварианты, [[work-card-state-machine]] — допустимые переходы, а [[roles-permissions]] — субъектов команд. Противоречие должно быть устранено до перевода артефактов в `accepted`.

## Вне правил MVP v1

- отклонение БТК и возврат на доработку;
- спор, изменение и версионность нормы;
- перевыпуск карточек;
- переназначение исполнителя;
- реальные payroll-расчёты и интеграции.
