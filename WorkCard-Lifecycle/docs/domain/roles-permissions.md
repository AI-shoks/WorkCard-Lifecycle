# Roles and Permissions

Матрица предметных полномочий MVP v1. Она определяет backend-авторизацию бизнес-действий; скрытие кнопки в UI лишь отражает это решение и не заменяет проверку.

## Модель демонстрационной идентичности

- система содержит заранее подготовленных синтетических пользователей;
- один demo-пользователь может переключать активную роль для демонстрации сценария;
- каждый запрос передаёт идентичность и активную роль через выбранный на этапе архитектуры механизм;
- backend проверяет роль для каждой команды и не доверяет роли, присланной произвольным полем тела запроса;
- управление реальными аккаунтами, паролями, подразделениями и сложными наборами ролей не входит в MVP.

## Роли

| Роль | Назначение | Ограничение |
|---|---|---|
| `PLANNER` | Создать синтетическую партию и выпустить карточки. | Не назначает и не выполняет карточки. |
| `MASTER` | Массово назначить карточки и подтвердить выполненную работу. | Не выполняет работу и не подтверждает качество. |
| `WORKER` | Начать и завершить назначенную работу. | Действует только над карточкой, где `assigneeId = actorId`. |
| `QUALITY_CONTROLLER` | Подтвердить качество после мастера. | В MVP может только подтвердить; отклонение отсутствует. |
| `ADMIN_AUDITOR` | Просмотреть аудит и выполнить mock payroll export. | Не меняет производственный жизненный цикл карточки. |

## Матрица команд

Обозначения: `✓` — разрешено при выполнении предметных предусловий; `own` — только назначенному исполнителю; `—` — запрещено.

| Команда | Planner | Master | Worker | Quality Controller | Admin / Auditor |
|---|:---:|:---:|:---:|:---:|:---:|
| `CreateProductionBatch` | ✓ | — | — | — | — |
| `ReleaseWorkCards` | ✓ | — | — | — | — |
| `AssignWorkCards` | — | ✓ | — | — | — |
| `StartWorkCard` | — | — | own | — | — |
| `CompleteWorkCard` | — | — | own | — | — |
| `ConfirmWorkCardByMaster` | — | ✓ | — | — | — |
| `ConfirmWorkCardQuality` | — | — | — | ✓ | — |
| `ExportWorkCardToPayroll` | — | — | — | — | ✓ |

Даже разрешённая по роли команда отклоняется при неверном состоянии, владельце, версии или входных данных.

## Матрица чтения

| Данные | Planner | Master | Worker | Quality Controller | Admin / Auditor |
|---|:---:|:---:|:---:|:---:|:---:|
| Список и карточка партии | ✓ | ✓ | ✓ | ✓ | ✓ |
| Список и детали `WorkCard` | ✓ | ✓ | ✓ | ✓ | ✓ |
| История / audit log карточки | — | — | — | — | ✓ |
| `PayrollRecord` | — | — | — | — | ✓ |

Широкое чтение синтетических производственных данных принято ради прозрачного demo-сценария. Реальная модель видимости по подразделениям и назначениям находится вне MVP.

## Проверки владения

Для `StartWorkCard` и `CompleteWorkCard` одновременно выполняются три независимые проверки:

1. активная роль равна `WORKER`;
2. `actorId` равен `WorkCard.assigneeId`;
3. состояние и `expectedVersion` допускают команду.

Наличие роли `WORKER` без совпадения исполнителя недостаточно. Мастер, планировщик, БТК и администратор не могут выполнить команду от имени исполнителя.

## Порядок backend-проверок

Для единообразного и безопасного поведения обработчик команды:

1. устанавливает доверенную идентичность и активную роль;
2. проверяет право роли на тип команды;
3. загружает целевые агрегаты;
4. проверяет владельца, состояние и бизнес-инварианты;
5. проверяет версии всех затронутых агрегатов;
6. применяет изменение и audit event в транзакции.

API не должен раскрывать чувствительные подробности существования недоступного объекта. Точная модель ответов `403/404/409` будет закреплена в [[api-contracts]] и negative scenarios.

## UI-поведение

- UI скрывает недоступные для активной роли действия;
- при известном, но временно недоступном действии UI может показывать disabled-состояние с причиной;
- переключение demo-роли обновляет доступные действия, но не изменяет предметные данные;
- ответ backend об отказе является окончательным, даже если UI ошибочно показал кнопку.

Подробности будут развиты в [[permission-ux]].

## Явно запрещено

- доверять роли или `assigneeId`, изменённым клиентом без серверной проверки;
- разрешать `ADMIN_AUDITOR` обходить state machine ради удобства демонстрации;
- позволять мастеру выполнять работу за исполнителя;
- позволять БТК подтверждать карточку до мастера;
- предоставлять отдельную команду закрытия без подтверждения БТК;
- добавлять отклонение БТК или переназначение без изменения scope.
