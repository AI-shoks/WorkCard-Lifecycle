# AS-IS and TO-BE

Этот документ сравнивает условный исходный процесс и целевой цифровой workflow MVP v1. AS-IS является проектной моделью проблемы для портфолио, а не результатом обследования конкретного предприятия.

## Граница анализа

Рассматривается путь одного экземпляра работы: планирование синтетической партии, выпуск карточки, назначение, выполнение, две контрольные точки, закрытие и демонстрационный экспорт нормо-часов. Склад, оборудование, материалы, реальные MES/ERP и расчёт зарплаты находятся вне [[mvp-scope]].

## Условный AS-IS

В исходной модели сведения о партии, экземплярах, назначениях и подтверждениях могут находиться в разных таблицах, сообщениях или бумажных формах. Это не позволяет считать один источник каноническим.

| Шаг | Условное выполнение | Основная проблема |
|---:|---|---|
| 1 | Планировщик передаёт сведения о партии и количестве экземпляров. | Нет гарантии, что на каждый экземпляр заведена отдельная прослеживаемая карточка. |
| 2 | Мастер распределяет работу между исполнителями вручную. | Трудно быстро определить актуального ответственного и обнаружить частичное назначение. |
| 3 | Исполнитель сообщает о начале и завершении работы отдельным каналом. | Состояние работы не связано с формальными предусловиями и может трактоваться неоднозначно. |
| 4 | Мастер и БТК последовательно подтверждают результат. | Порядок контрольных точек и полномочия не защищены единым механизмом. |
| 5 | Сведения о завершённой работе передаются для учёта нормо-часов. | Повторная передача может создать дубль, а основание начисления трудно восстановить. |
| 6 | История собирается из нескольких источников. | Нельзя надёжно восстановить, кто, когда и на каком основании изменил состояние. |

### Наблюдаемые риски AS-IS

- количество рабочих карточек расходится с количеством экземпляров партии;
- назначение применяется только к части выбранных карточек;
- пользователь выполняет действие вне своей роли или над чужой карточкой;
- контрольные точки проходят в неправильном порядке;
- конфликтующие изменения незаметно перезаписывают друг друга;
- одна работа дважды попадает в демонстрационное начисление;
- история не объясняет текущее состояние.

## Целевой TO-BE для MVP v1

Production Work Card Workflow становится единым источником состояния для демонстрационного сценария. Каждое изменение выполняется именованной бизнес-командой, проверяется на backend и сопровождается событием аудита.

| Шаг | Целевой процесс | Контроль результата |
|---:|---|---|
| 1 | Планировщик создаёт синтетическую партию с количеством, маршрутом и нормативом. | Входные данные проходят валидацию; партия получает уникальный идентификатор. |
| 2 | Планировщик выпускает карточки партии. | Создаются один `WorkCardSet` и ровно `N` уникальных `WorkCard`; повторный выпуск запрещён. |
| 3 | Мастер массово назначает выбранные карточки исполнителю. | Команда атомарна: применяются все назначения либо ни одно. |
| 4 | Назначенный исполнитель начинает и завершает работу. | Backend проверяет роль, владельца, состояние и ожидаемую версию карточки. |
| 5 | Мастер подтверждает выполненную работу. | Карточка переходит к контролю качества только из допустимого состояния. |
| 6 | Контролёр БТК подтверждает качество. | Положительное подтверждение атомарно закрывает карточку; отклонение не входит в MVP v1. |
| 7 | Система фиксирует закрытую карточку. | Закрытие является результатом подтверждения БТК, а не отдельным ручным действием. |
| 8 | Администратор запускает mock payroll export. | Только закрытая карточка создаёт одну запись начисления; повторная команда идемпотентна. |
| 9 | Пользователь просматривает историю карточки. | Audit log показывает последовательность значимых действий и их субъектов. |

## Изменение ответственности

| Область | AS-IS | TO-BE |
|---|---|---|
| Источник состояния | Разрозненные записи | `WorkCard` как каноническая единица жизненного цикла |
| Допустимость действий | Зависит от ручной дисциплины | State machine и backend permissions |
| Массовые операции | Возможен частичный результат | Транзакционная атомарность |
| Конкурирующие изменения | Могут быть незаметны | Проверка ожидаемой версии |
| История | Собирается постфактум | Audit event сохраняется вместе с изменением |
| Передача нормо-часов | Возможны дубли | Идемпотентный mock export |

## Что TO-BE намеренно не решает

- отклонение БТК и возврат на доработку;
- спор и версионность нормы;
- повторный выпуск карточек;
- интеграцию с реальной payroll, MES или ERP;
- расчёт зарплаты и фактического рабочего времени;
- управление реальными учётными записями предприятия.

Эти ограничения сохраняют границу MVP и не должны скрыто появляться в [[domain-model]], [[business-rules]] или [[work-card-state-machine]].
