# Document Governance

Эта политика предотвращает дубликаты, устаревшие решения и ситуацию, когда несколько заметок одновременно выглядят действующими.

## Основной принцип

У каждого смыслового артефакта есть один стабильный `artifact_id` и один канонический путь. Дата изменения сама по себе не определяет актуальность: источником истины являются `artifact_id`, `status` и явные связи замещения.

## Обязательный frontmatter

```yaml
---
artifact_id: product.mvp-scope
status: accepted
version: 1
owner: product
updated: 2026-07-17
supersedes: null
superseded_by: null
---
```

Поля `supersedes` и `superseded_by` добавляются только при фактическом замещении отдельного документа.

## Допустимые статусы

| Статус | Значение |
|---|---|
| `planned` | Артефакт запланирован, работа не начата |
| `draft` | Содержание формируется |
| `in-review` | Артефакт проверяется перед принятием |
| `accepted` | Действующая каноническая версия |
| `superseded` | Документ заменён другим, указан `superseded_by` |
| `rejected` | Предложение рассмотрено и отклонено |
| `archived` | Документ больше не относится к активному проекту |
| `active` | Постоянно обновляемый операционный документ: план, backlog, журнал или реестр |

## Living documents

Product brief, MVP scope, glossary, domain model, business rules и другие описания текущего состояния обновляются **на существующем каноническом пути**. При существенном изменении:

1. увеличить `version`;
2. обновить `updated`;
3. записать причину в [[decision-log]] или ADR;
4. проверить связанные требования, тесты и диаграммы.

Копии вида `mvp-scope-new.md`, `mvp-scope-final.md` и `mvp-scope-v2-final.md` запрещены.

## Decisions and ADR

До merge review-ветки в каноническую ветку accepted ADR может быть скорректирован по результатам review с повышением версии и отдельным correction commit. Причина должна быть зафиксирована в [[decision-log]] или review.

После merge в каноническую ветку изменение принятого архитектурного решения выполняется только новым ADR:

1. создаётся новый ADR;
2. старый получает `status: superseded` и ссылку `superseded_by`;
3. новый получает ссылку `supersedes`;
4. ссылки `supersedes` и `superseded_by` взаимны;
5. оба документа сохраняются как история причин и последствий.

## Правила уникальности

- один `artifact_id` принадлежит только одному каноническому файлу;
- для одного предмета не может быть двух документов со статусом `accepted`;
- имя файла не используется для создания временных версий;
- новый файл создаётся только для нового артефакта или нового неизменяемого решения;
- устаревший документ нельзя оставлять без статуса и ссылки на замену.

## Архивирование и удаление

- устаревшие решения помечаются, а не удаляются;
- временные рабочие заметки после переноса полезной информации могут быть удалены вручную;
- удаление канонического или исторического документа требует проверки входящих ссылок;
- будущая автоматизация может находить конфликты и предлагать действия, но не должна самостоятельно удалять файлы.

## Проверка перед завершением этапа

- нет повторяющихся `artifact_id`;
- нет двух принятых документов об одном артефакте;
- каждый `superseded` документ указывает замену;
- ссылки `supersedes` и `superseded_by` взаимны;
- нет битых Obsidian-ссылок;
- `updated` соответствует последнему смысловому изменению;
- изменения принятых решений отражены в журнале или ADR.

## Project Docs Auditor

Личный skill `$project-docs-auditor` создан и установлен. Он выполняет структурные проверки, формирует отчёт и предлагает безопасные исправления. Skill не удаляет и не переписывает документы автоматически; семантические противоречия проверяются отдельным осмысленным проходом.

Перед закрытием этапа следует вызвать `$project-docs-auditor` для корня проекта и потребовать строгий режим без предупреждений.
