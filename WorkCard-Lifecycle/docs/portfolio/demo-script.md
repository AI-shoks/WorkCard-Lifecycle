# Сценарий демонстрации

Два формата: короткий рассказ с живым интерфейсом и сохранёнными результатами либо полный воспроизводимый проход через браузер, API и PostgreSQL. Ожидаемые действия ниже не являются заявлением о новой приёмке текущего checkout. Фактические результаты связаны с версиями в [[quality-gates]] и [[deployment]].

## Короткий показ

**5–7 минут после загрузки демо.** Откройте [публичное приложение](https://work-card-demo.onrender.com), [снимки экранов](screenshots.md) и [README со схемой](../../README.md#архитектура). Render может просыпаться после простоя; если API закрыт из-за обслуживания или квот, покажите сохранённые материалы с их датой. Для рассказа не нужны reset, создание облачных ресурсов или изменение инфраструктуры.

Публичная БД общая; её очистка запланирована ежедневно, но расписание может дать сбой. Не рассчитывайте на наличие вчерашней партии или компактного паспорта на шесть карточек: он использовался в отдельной проверке recovery, затем удалён. Не создавайте впечатление, что все 250 карточек можно вручную завершить за время короткого показа.

Если нужна живая команда, заранее подготовьте **свою локальную** партию через обычный UI по полному сценарию ниже. Во время показа проведите одну первую деталь и покажите изменение допуска её комплекта. Остальные карточки и итоговую приёмку показывайте как сохранённый результат, пока не выполнен весь процесс. Не подменяйте состояния JavaScript, SQL или mock-ответами.

## Полный воспроизводимый проход

Далее — подробная последовательность для отдельной проверки или подготовки демонстрации. Она намеренно не входит в обещанные 5–7 минут. Compact и canonical — разные fixtures; доказательства на шести карточках не подменяют проход всех 250.

## Подготовка

Запустите текущий checkout по [[local-development]] в отдельном чистом окружении. PostgreSQL должен содержать миграции и подготовленные reference data, но не готовую производственную партию. Для повторной проверки используйте новую disposable БД/Compose project: существующие пользовательские volumes не удаляются без отдельного решения.

Откройте приложение, убедитесь в готовности среды и выберите подготовленную роль. Для всех шагов используйте кнопки и диалоги SPA: backend определяет actor, разрешения, state, gate и версии. Не подставляйте ответы API, готовые состояния карточек или финальную приёмку через JavaScript/SQL. Документационный [14-шаговый прототип](../ux/prototype.html) проверяется отдельно и не заменяет этот проход.

## Партия и выпуск

1. Выберите «Специалист ПДБ», откройте «Новая партия», выберите подготовленный паспорт. Проверьте read-only группы операций, количества карточек и нормы.
2. Введите `112` изделий и создайте партию. После серверного ответа и контрольного чтения откроется партия «Не выпущена».
3. Проверьте preview: `112 изделий → 3 комплекта → 250 карточек`; план комплектов — `112`, `112`, `26`.
4. Нажмите «Выпустить все комплекты» и подтвердите однократный выпуск. Дождитесь полного read-back. Должны появиться все три комплекта с исходными нормами и ожидающей первой деталью, а повторный выпуск — стать недоступен.

## Первая деталь и распределение

1. Выберите «Мастер участка» и откройте первый полный комплект из `112` карточек. Выберите ровно одну доступную карточку и назначьте её пользователю «Исполнитель Иванов» для первой детали с явным подтверждением.
2. Откройте назначенную карточку. Мастер последовательно фиксирует начало и завершение; каждый следующий шаг доступен только после подтверждённого сервером состояния.
3. Переключитесь на контролёра БТК. Подтвердите положительную приёмку первой детали в диалоге. Проверьте оба результата: карточка закрыта, обработка партии в её комплекте разрешена.
4. Вернитесь к мастеру. Выберите ещё `59` доступных карточек этого комплекта для пользователя «Исполнитель Иванов» и подтвердите назначение. Отдельной командой назначьте оставшиеся `52` пользователю «Исполнитель Петров». Если все доступные карточки ещё не загружены, используйте подгрузку страниц; число выбора относится к доступной выборке, а не к диапазону номеров деталей.
5. Проверьте подтверждённое распределение: `1 + 59 + 52 = 112`, Исполнитель Иванов — `60`, Исполнитель Петров — `52`. В списке нет номеров физической детали, диапазонов `1–60`/`61–112` или UUID в основном тексте.
6. Переключитесь на каждого рабочего: доступна только его назначенная работа, кнопок начала/завершения и БТК нет. При смене роли прежние выделение, диалог и защищённые данные исчезают.

## Завершение всех карточек

1. Для одной назначенной карточки обработки партии мастер фиксирует начало и завершение, затем БТК отдельно подтверждает качество. Закрывается только эта карточка; подсказка различает цифровое закрытие, финальную приёмку партии и физические подписи БТК.
2. Проведите первую деталь второго и третьего комплектов тем же порядком: назначение → мастерское начало → мастерское завершение → положительная приёмка БТК. После каждой приёмки перечитываются карточка и соответствующий комплект.
3. Назначьте оставшиеся карточки каждого открытого комплекта одному из подготовленных исполнителей. Каждая команда выбора ограничена одним комплектом и подтверждается отдельно.
4. Для всех оставшихся карточек мастер фиксирует начало и завершение; затем БТК подтверждает качество каждой карточки отдельно. Повторение выполняется через те же реальные UI-команды, без массового обхода lifecycle и подстановки готового `CLOSED` состояния.
5. Вернитесь к партии. Контрольные итоги канонического паспорта: принятые первые детали `3 из 3`, закрытые обязательные карточки `250 из 250`, финальная приёмка ещё не записана. До этих итогов действие БТК должно быть недоступно с точной причиной.

## Финальная приёмка

1. Контролёр БТК нажимает «Принять завершённую партию» и отдельно подтверждает решение.
2. Дождитесь серверного ответа и полного read-back. Партия показывает финальную приёмку, контролёра и время сервера. В «Сведениях о прототипе» раскройте вложенные «Технические коды для разработчика» и сверьте acceptance ID, command ID и результирующую версию.
3. Обновите страницу: должна читаться та же неизменяемая acceptance. Новое принятие недоступно. Backend replay того же command ID должен возвращать исходную запись без нового события; для этого есть тест API integration suite, не требующий кнопки повтора в UI. Результаты его выполнения учитываются только вместе с версией и окружением в [[quality-gates]].

## Полный журнал действий

1. Выберите «Администратор-аудитор», откройте закрытую карточку и «Журнал действий».
2. Проверьте русские названия событий, actor/time и порядок истории. Откройте контекст события выпуска карточки: серверный query по correlation должен загрузить все страницы операции, а не только историю выбранной карточки.
3. Для канонического выпуска ожидается `254` события: одно партии, три комплектов и `250` карточек. Отображённый полный набор должен совпасть с authoritative totals и общими command/correlation IDs; технические значения доступны только во вложенном developer context.
4. Проверьте также контекст массового назначения и первой приёмки. Их данные охватывают все затронутые агрегаты, а не объединение известных клиенту историй. Неполный ответ должен показывать ошибку целостности.

## Тестовый учёт нормо-часов

1. Из закрытой карточки перейдите в «Тестовый учёт нормо-часов». Переход читает карточку и существующую запись; сам переход не экспортирует норму.
2. Если записи ещё нет, нажмите «Создать тестовую запись нормо-часов». Проверьте группу операций, исполнителя и норму, затем отдельно подтвердите создание в диалоге.
3. Дождитесь обязательного read-back. Запись должна содержать того же исполнителя и operation-scoped снимок нормы, администратора и время. Денежные расчёты отсутствуют.
4. Повторно откройте/обновите экран. Он должен показывать ту же запись без нового export и нового начисления. Если при гонке backend вернул существующую запись, UI также сообщает о существующем результате. Replay/concurrent export и отсутствие дубликата покрыты интеграционными тестами; наличие теста не заменяет успешный результат конкретного прогона в [[quality-gates]].

## Проверки интерфейса и восстановления

- Пройдите роли и основные экраны на desktop и mobile, проверьте переносы, доступность кнопок, `aria-*`, причины disabled и browser console.
- Чужие действия скрыты; прямые audit/payroll URLs у производственных ролей показывают безопасный отказ без загрузки защищённых данных.
- При устаревших версиях или сетевой неопределённости успех не заявляется: UI очищает диалог/selection и выполняет только безопасные чтения всех целей. При неудаче чтения команды заблокированы, доступен явный повтор чтения. Новая команда требует нового решения и подтверждения.
- Отдельно откройте документационный прототип, пройдите все `14` шагов на desktop/mobile и запустите `window.runUxCopyAudit()`. Его результат не является подтверждением выполнения domain-команд в PostgreSQL.

Сценарий сохраняет [[mvp-scope]]: отрицательная приёмка, доработка, переназначение, повторный выпуск, редактирование норм и реальные выплаты отсутствуют.

## Отложенная ручная проверка этапа 12

Статический аудит 27 сентября 2026 года сверил сценарий с командами, интерфейсом, конфигурацией и сохранёнными доказательствами. Последующая работа закрыла FA-01/02 локальными unit/API/PostgreSQL проверками текущего незакоммиченного дерева — [[final-audit]]. 27 сентября получено подтверждение пользователя «все проверил, все работает»; прежний отложенный ручной пункт отмечен выполненным. SHA/окружение не указаны; сообщение не заменяет результат полного canonical lifecycle и не переносится на изменённый код. Публичный образ не менялся. Ниже сохранён справочный чек-лист для повторного показа:

- Зафиксировать проверяемые SHA/локальные изменения, дату и окружение; запустить по [[local-development]], проверить SPA, liveness и readiness. Для публичного демо отдельно указать его release version.
- Пройти короткий показ за 5–7 минут: роль ПДБ, паспорт `112 → 3 → 250`, собственная подготовленная карточка либо подписанные исторические снимки, схема, evidence и ограничения.
- Проверить основные экраны и смену ролей на desktop/mobile, отсутствие ошибок Console/Network и доступность действий только своей роли.
- Если подтверждается текущий полный lifecycle, пройти подробный сценарий выше в отдельном окружении: `250/250`, отдельная финальная приёмка, `254` события выпуска, одна запись нормо-часов после повторного чтения. Просмотр скриншота или шесть compact-карточек этот результат не заменяет.
- Записать фактический результат и замечания в [[backlog]]/[[project-plan]], явно указав, что именно проверено. Локальное закрытие FA-01/02 не закрывает этап 12 и roadmap: требуется отдельное решение по полному DoD и квалификации выбранной версии.

Короткий целевой UI-smoke после FA-01/02 выполнен агентом через Computer Use 27 сентября; артефакты и 22/22 hashes сверены 28 сентября — [[final-audit]]. Подтверждены выпуск 250/audit 254, первая карточка и открытый gate, две payroll-команды с одной записью и событиями 1/0, отдельная финальная приёмка и повторное чтение. Финальная партия подготовлена API/SQL; её 250 закрытий не являются UI lifecycle. Кнопки активировались клавиатурой из-за ограничения мышиных действий инструмента. Это отдельный результат агента, не прежнее подтверждение пользователя. Повтор короткого smoke на тех же исходниках не требуется; обязательные CI checks выбранной версии и границы будущего релиза описаны в FA-03.
